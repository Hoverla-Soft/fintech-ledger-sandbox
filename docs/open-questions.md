## API gaps the console works around (opened Phase 5a)

Each of these is a capability the console needs and the API does not currently provide. None is a defect: the API is correct as specified, and the console has a working — sometimes visibly compromised — answer for each. They are recorded so the compromise is a decision on the record rather than an accident, and so Phase 6 has a shortlist.

| 28 | ~~**Operational hardening absent in `apps/server`.**~~ **Fully resolved 2026-08-17.** SIGTERM/SIGINT drain then close the pool; `/ready` queries Postgres while `/` stays dependency-free; a 1 MB body limit runs before parsing. ~~**Still open: `createDb` sets no `statement_timeout`, no `idle_in_transaction_session_timeout`, and no connection timeout**~~ — all three now set | **Fully resolved 2026-08-17** | **The timeouts (closed 2026-08-17).** `statement_timeout: 10s`, `idle_in_transaction_session_timeout: 30s`, `connectionTimeoutMillis: 5s`, passed through drizzle's `{ connection: PoolConfig }` form. The fix was registration order, not new code. (2) **The remaining timeout is genuinely delicate, not merely unscheduled.** `statement_timeout` *does* abort a statement blocked on a lock — including the idempotency reservation's deliberate wait (`reserve-key.ts` uses a plain blocking `INSERT` precisely so the loser blocks until the winner commits), verified empirically against postgres 18. A bound is still correct because `postTransaction` runs inside one transaction, so a timeout rolls back whole rather than partially, and the caller holds an idempotency key making retry safe — an abort costs a retry, not a correctness violation. That argument is what makes ~10s defensible and 1s not, and it must be re-checked before any code blocks on a lock *outside* a transaction.
