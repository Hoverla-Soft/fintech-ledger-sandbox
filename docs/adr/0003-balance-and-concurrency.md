# 0003 — Balance and concurrency strategy

**Status:** Accepted (Phase 3)

## Context

`packages/core` (Phase 2) proved the invariants a pure domain can enforce. Five more only a database can enforce: `docs/product/requirements/ledger.md`'s **#2 balances reconcile**, **#3 atomicity**, **#4 idempotency** (ADR 0004), **#5 no cross-tenant leakage**, and **#8 immutable history**. This ADR covers the first, third, and fifth; ADR 0004 covers idempotency.

A ledger balance can be modeled two ways: computed on read (sum every posting each time a balance is needed) or materialized and kept in sync. Pure computed-on-read never drifts by construction, but it does not scale to a long posting history and gives concurrent writers nothing to lock — two transfers touching the same account would both read a stale balance and could both succeed when only one should. A materialized balance needs a locking strategy to stay correct under concurrent writers, and needs its own drift-detection story, since nothing forces it to stay equal to the posting history it is supposed to summarize.

Multi-account transfers also raise a classic locking hazard: if transfer A locks account 1 then account 2, while a concurrent transfer B locks account 2 then account 1, both can block waiting on the other's lock — a deadlock.

Invariant #8 (append-only postings) and invariant #5 (tenant isolation) both need enforcement that does not rely on every caller remembering the rule — a repository could be written correctly today and violated by the next change without a database-level backstop.

## Decision

**Materialized balance, continuously-asserted reconciliation.** `ledger_account.balance` is a materialized `bigint` column, updated inside the same transaction that inserts postings. `ledger_posting` is append-only and is the source of truth; `reconcileAccounts` (`packages/db/src/repositories/reconciliation.ts`) recomputes `signed Σ(postings)` per account (debit positive, credit negative, matching `core`'s `signedAmount` convention) and compares it against the materialized balance on demand. This is an invariant a caller can assert at any time, not a periodic batch job — there is no scheduled reconciliation sweep; correctness is meant to hold continuously as postings write, and `reconcileAccounts` is how a caller (or a test) checks it.

**Ordered row locks.** `lockAccounts` (`packages/db/src/posting/lock-accounts.ts`) locks every account a transaction touches with one `SELECT ... FOR UPDATE WHERE org_id = $1 AND id = ANY($2)`, after de-duplicating and **sorting** the account ids first. Two concurrent transfers touching the same account pair — even in opposite directions — always request their locks in the same relative order, so neither can hold one lock while waiting on the other: deadlock is structurally impossible, not just unlikely.

The `org_id` predicate on that same query is invariant #5's enforcement point: an account belonging to another org simply does not match a row, so it is reported as the identical `AccountNotFound` a genuinely missing id would produce. Nothing about another tenant's data — not even its existence — leaks through this function.

**The funds rule is reused, never restated.** Once accounts are locked, `postTransaction` (`packages/db/src/posting/post-transaction.ts`) calls `core.applyDelta(account, balance, delta)` for each account `Transaction.deltas()` touches. `applyDelta` is where invariant #6 (a `normal` account may never go negative) actually lives; the persistence layer trusts that check instead of writing an equivalent `WHERE balance + delta >= 0` in SQL. Restating the rule in two places is exactly the drift ADR 0002 already rejected for money representation.

**Composite foreign keys enforce tenant isolation structurally.** `ledger_posting` has no plain FK from `account_id` to `ledger_account.id`; instead `foreignKey({ columns: [accountId, orgId], foreignColumns: [ledgerAccount.id, ledgerAccount.orgId] })`, backed by a unique `(id, org_id)` constraint on `ledger_account`. The same shape applies to `transaction_id`. A posting whose `org_id` disagrees with its account's or transaction's real owning org is rejected by Postgres itself — invariant #5 is not only an application-level `WHERE org_id = ...` habit, it is a constraint the database enforces even if a future code path forgets the predicate.

**Invariant #8 needs two triggers, not one.** `ledger_posting_block_mutation()` (`packages/db/drizzle/0002_ledger_posting_immutability_trigger.sql`) raises on any attempt to mutate a posting. A row-level `BEFORE UPDATE OR DELETE ... FOR EACH ROW` trigger looked sufficient at first, but `TRUNCATE` in Postgres **never fires row-level triggers** — `TRUNCATE ledger_posting`, or a `TRUNCATE ... CASCADE` cascading from `organization`, would have silently wiped append-only history despite the row-level trigger being in place. This was a real gap caught in review, not a theoretical one. The fix is a second, statement-level `BEFORE TRUNCATE ... FOR EACH STATEMENT` trigger backed by the same function (the function references neither `NEW` nor `OLD`, so one function body backs both trigger forms).

**Rejections need a second, separate transaction.** `ledger.md` requires that a failed transfer be *recorded* while guaranteeing that no postings are written for it. Those two requirements pull against each other inside a single transaction: an audit row inserted before the failure is discovered rolls back along with everything else the moment Postgres aborts the transaction, leaving the rejection log silently empty exactly when it matters most. `postTransaction` resolves this by rolling the failing attempt back first, then writing the `outcome = 'rejected'` audit entry in a brand-new transaction, in `writeRejectionAudit`. This is the one place in the routine where "atomic" (the failed attempt writes nothing) and "recorded" (the failure itself is never lost) cannot both be satisfied by one transaction, and the resolution is deliberate: two transactions, one for the attempt, one for the fact that it failed.

## Consequences

- **Pro:** deadlock-free multi-account transfers by construction (sorted lock order), not by retry-and-hope.
- **Pro:** the funds rule and the reconciliation sign convention each have exactly one implementation (`core.applyDelta`, `core.signedAmount`) that persistence depends on and never re-derives.
- **Pro:** tenant isolation for postings is enforced by the database's own constraint system, not solely by every repository remembering an `org_id` filter.
- **Pro:** immutability holds against `UPDATE`, `DELETE`, and `TRUNCATE` alike — the gap that a single row-level trigger would have left is closed.
- **Con — blocked hard-deletion of a user who has ever posted:** `ledger_transaction.created_by` and `ledger_audit_entry.actor_user_id` both reference `user.id` with no `onDelete` cascade (the default, "no action"). This is deliberate — financial provenance ("who posted this transfer") must survive that user's own account being deleted — but the practical effect is that hard-deleting such a user is **permanently blocked**: Postgres raises a plain foreign-key violation, not a typed application error, the moment the delete runs. A future phase needing user deletion must either pre-check for any transaction/audit row the user authored, or commit to "deactivate, never hard-delete" as the actual account-closure model. Neither is decided yet.
- **Con — trigger-based immutability is a database-level guarantee only against an ordinary application role.** A sufficiently privileged Postgres role can bypass it entirely — `ALTER TABLE ledger_posting DISABLE TRIGGER ledger_posting_immutability_trigger`, or setting `session_replication_role = replica` for a session, both suppress trigger firing. Real enforcement therefore requires a second control this ADR does not provide: the application's runtime database role must itself lack `ALTER TABLE` and superuser/replication privileges on `ledger_posting`. That is a role-provisioning decision, and as of this phase it has no owner in `docs/operations/` or `docs/development/infrastructure.md` — the trigger is real, but who is responsible for making sure the app connects with a role that cannot disarm it is an open question.
