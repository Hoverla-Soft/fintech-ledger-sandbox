# 0006 — Write endpoint contract

**Status:** Accepted (Phase 4b)

## Context

Phase 4a shipped the read surface, the tenancy middleware, the role ladder, and the full error map, but no procedure that writes anything. Phase 4b adds three — `accounts.create`, `transactions.create`, `transactions.reverse`, all on `adminProcedure`. ADR 0003 and ADR 0004 already settled what happens once a write reaches `packages/db`: ordered row locks, materialized balances, a blocking `INSERT` against `UNIQUE (org_id, key)`, and replay-versus-conflict decided by comparing a stored `request_hash`. Neither ADR says anything about what the *caller* sends, and that is what this one records.

Three of these choices are unusually expensive to revisit later. The `request_hash` derivation is **persisted** in `ledger_idempotency_key` and compared against on every retry, so changing how it is computed invalidates every key already in the database. The input schemas are a published contract — the Phase 5 console and the OpenAPI reference are both generated from them. And the reversal semantics decide whether an operation is possible at all, not merely how it is spelled.

## Decision

**The request hash is SHA-256 hex over canonical JSON of the validated domain payload.** `computeRequestHash` (`packages/api/src/contracts/request-hash.ts`) takes the constructed `Transaction`, not the request body — the hash describes what the ledger will actually do, not how the caller happened to phrase it.

Getting this wrong breaks idempotency *silently*, and it fails in two opposite directions depending on which way it is wrong.

**Too sensitive → a false `409` on an honest retry.** A client posts a three-leg payroll split, the connection times out before the response arrives, and it retries under the same key. Its second serialization emits the legs in a different order (a different SDK, a re-serialized form, a `Map` iteration) or spells the amount `"10.0"` where the first attempt sent `"10.00"`. Both requests are the same request: `Transaction.deltas()` nets by account before anything is persisted, and `Money.parse` treats both strings as the same amount, so the ledger effect is byte-identical. But if the hash covered the caller's array order or its raw amount strings, the stored hash and the retry's hash differ, `reserveIdempotencyKey` reports `IdempotencyConflict`, and the caller gets `409 idempotency_conflict` with a message asserting the key was used with a *different payload* — which is false. The client is then stuck: it cannot retry under that key, and retrying under a fresh key posts the payroll twice, which is exactly the double-post invariant #4 exists to prevent. So legs are sorted by `(accountId, direction, amount, currency)` before hashing, and amounts are normalized through `Money.format()`.

**Too loose → a replay for a request that was not the same.** Suppose amounts were omitted from the hash. A client retries under the same key having corrected the transfer from `500.00` to `5000.00`; the hash still matches, so the ledger replays the *original* transaction and answers `200` with a real transaction id and real postings. The client books `5000.00` as posted; the ledger holds `500.00`; nothing raises anywhere, and the divergence surfaces only at reconciliation against an external system. `reversesTransactionId` is in the hash for the same reason and is not hypothetical: two identical transfers A and B produce mirrored leg sets that are identical, so a client that reverses A under key `k` and then mistakenly reuses `k` to reverse B would be handed A's reversal back as a replay. B stays un-reversed while the caller believes it succeeded.

Amounts are decimal **strings**, never JSON numbers: `bigint` throws in `JSON.stringify`, and a JSON number reintroduces precisely the IEEE-754 error ADR 0002 exists to prevent. `idempotencyKey` is excluded because it is the lookup key — including it would make every hash trivially unique and defeat the comparison. `orgId` is excluded because `UNIQUE (org_id, key)` already scopes the key per tenant. `actorId` is excluded because ADR 0004 speaks of "the same payload," and who submitted a request is not part of the payload. The canonical string is built by hand rather than `JSON.stringify`'d over an object literal, because `JSON.stringify` preserves insertion order — a future refactor that swapped two properties in a literal would change every hash and invalidate every stored key without touching a line of logic anyone would think to review.

**The idempotency key travels in the request body**, as a field of the input schema, not an `Idempotency-Key` header. `ledger.md` line 47 lists it alongside source, destination, and amount. A header would require changing `Context`, which carries no headers today, and every fixture in the suite, and it would be invisible both to `no-org-input.test.ts`'s schema introspection and to the generated OpenAPI reference. A header alias can be added later without breaking this.

**`transactions.create` takes a raw postings array**, not a `{source, destination, amount}` transfer shape. It maps 1:1 onto `Transaction.create`, so no translation layer of ours can introduce an imbalance of its own. The decisive argument is not elegance: `too_few_postings` and `unbalanced_transaction` are **published** reasons in `docs/backend/error-handling.md`, and a transfer shape makes both structurally unreachable — a two-account shape can never produce fewer than two legs, and a single amount mirrored across two legs can never fail to net to zero. Adopting it would turn two entries of the documented error contract into dead code that no test could exercise. The array bound follows from the same reasoning: `MAX_POSTINGS` caps it at 100 so one request cannot demand unbounded row locks, but the floor is deliberately **0**, leaving `Transaction.create`'s `>= 2` rule as the thing that rejects a short set.

**Reversal takes its own caller-supplied idempotency key, and reversing a reversal is allowed.** Nothing in `ledger.md` forbids it, and re-applying a reversed transaction is legitimate. Deriving the key server-side from the original transaction id would overload the idempotency key with a business rule, and a legitimate second reversal would then surface as a `409` whose message ("used with a different request payload") would be untrue. A handler pre-check is racy; the only non-racy block is a partial unique index, which is a migration and out of scope for this phase. Two guardrails are not optional. The original is resolved through `getTransactionById(db, orgId, id)`, because `ledger_transaction`'s self-FK is **org-blind** — an unscoped lookup would let one tenant reverse another's transaction, and a cross-org id must return the same `404` a missing one does. And the mirrored legs are rebuilt from the **persisted rows**, never from the request body; the input carries only an id, so there is nothing for a caller to tamper with.

**Pre-persistence rejections are audited too.** `ledger.md` lines 54 and 65 require every rejection to be recorded, but validation failures at `Transaction.create` (unbalanced, fewer than two legs, non-positive, currency mismatch) happen in `packages/api` *before* `postTransaction` is ever called, so its internal rejection-audit path never sees them — and `IdempotencyConflict` returned early without auditing at all. `recordRejection` (`packages/db/src/repositories/audit.ts`) is now the single implementation of "write a rejection audit row," called from the handler for pre-persistence failures, from the conflict branch, and from `writeRejectionAudit` for failures discovered under the lock. The reason string comes from `reasonFor(error)`, the same `classify` the HTTP response is built from, so the log and the response can never name a failure differently. `accounts.create` writes no audit entry: `ledger.md` line 65's side-effect list describes the transaction path only.

**Balances in a write response are "current as of this response,"** not an as-of-posting snapshot. A fresh post computes them inside its own transaction; a replay re-reads `ledger_account.balance` live. One response shape serves both, and the semantics are stated in `postedTransactionSchema`'s `.describe()` so they reach the OpenAPI reference rather than being folklore.

## Consequences

- **Pro:** an honest retry replays regardless of leg order or amount spelling, so a client's serialization details can never manufacture a `409` it has no safe way to recover from.
- **Pro:** the hash is derived from the domain object, so it is impossible to hash a payload the ledger would have rejected, and impossible for a validation change to drift away from what was hashed.
- **Pro:** `too_few_postings` and `unbalanced_transaction` are reachable, testable, and therefore honestly documented; the published error contract has no dead entries.
- **Pro:** every rejection the API can produce now reaches `audit.rejections` with the same reason string the caller received, closing the two classes that were silently unrecorded before this phase.
- **Pro:** a cross-org reversal is indistinguishable from a missing one, and a reversal's legs cannot be influenced by the request that asks for it.
- **Con — excluding `actorId` lets one admin replay another's result.** Two admins in the same org who happen to submit the identical transaction under the same key do not conflict; the second is served the first's transaction and its id. This grants no access either lacked — both are already `adminProcedure`-authorized inside that tenant, and the key is org-scoped — but it does mean a write attributed to admin A can be handed back as a success to admin B, and `ledger_transaction.created_by` will name A. A client that uses a shared or predictable key scheme across operators will see this.
- **Con — the postings array diverges from `ledger.md` line 47**, which describes the submission as a transfer with source, destination, amount, and optional extra legs. The API does not take that shape. The line is annotated rather than left to contradict the code silently, but the divergence is real: line 47 describes the user-facing submission the Phase 5 console will compose, and composing it — including balancing the legs — is now the console's job, not the API's. Any client that wants transfer ergonomics has to build them itself.
- **Con — the API will reverse a reversal, and nothing stops a loop.** Each reversal is a fresh transaction with its own caller-supplied key, so a client that reverses X, then reverses that reversal, then reverses *that*, is never refused. A careless retry loop that generates a new key each time will happily post an unbounded chain of alternating mirrored transactions, each one valid and each one auditable, with the net effect flipping on every step. There is also no check that a transaction has already been reversed, so two reversals of the same original under two different keys both succeed and double the correction. Blocking this needs a partial unique index (a migration), which this phase does not ship.

  **Updated Phase 6b (2026-07-28) — partially addressed, and one clause here was wrong.** The *detectability* half is closed: `transactionSchema` now carries `reversedBy`, the inverse of `reversesTransactionId`, so a client can ask whether a transaction has been reversed and by what. Migration `0004` adds the partial index the lookup needs. The console's reversal dialog states "this transaction has already been reversed *n* times" instead of disclosing that it cannot tell — which is what this ADR assumed a console would do all along.

  The *prevention* half is deliberately still open: reversing remains permitted and undeduplicated, so `reversedBy` informs rather than blocks. Making a second reversal illegal is a product decision with its own migration, and 6b was explicitly scoped not to make it.

  The wrong clause: **"two reversals of the same original under two different keys both succeed"** is not unconditionally true. Each reversal re-applies the mirrored legs, so reversing a credit into a `normal` account twice drives that account negative and is refused for `insufficient_funds` (invariant #6) — discovered when the 6b double-reversal test failed for exactly that reason and had to fund the account first. Whether a second reversal succeeds depends on balances at the time, not on anything structural. That is also precisely why `reversedBy` is a **list** rather than a boolean: whether a second reversal exists is a runtime fact, not a schema-level one.
- **Con — the canonical string is now a persisted format with no version tag.** `request_hash` rows outlive the code that produced them, and nothing in the schema records which derivation wrote them. Any future change to `canonicalize`, to the sort order, or to `Money.format()` re-hashes every request differently while the stored hashes stay put, turning every honest retry against a pre-existing key into a `409`. The unit tests pin the current behavior, but there is no migration story for the stored hashes, and there is no marker that would make a mismatch diagnosable in production rather than merely confusing.
- **Con — the pre-persistence audit is best-effort.** `recordDomainRejection` swallows its own failure and logs it, on purpose: the caller is already receiving a correct `4xx` for the real problem, and turning a logging failure into a `500` would replace an accurate client error with a misleading one. The cost is that "every rejection is recorded" is a guarantee only up to the audit insert succeeding. It is also a separate top-level write, so a validation rejection costs an extra round trip even though nothing was ever going to be persisted.
- **Con — replay responses are not a snapshot, and look like one.** A client that diffs a replayed response against the original it cached will see identical postings alongside different `balances` and could reasonably conclude something changed. **Updated 2026-08-01:** `postedTransactionSchema` now carries `replayed: boolean`, so the console can say whether a second posting occurred. Balances remain current-as-of-response on replay; the flag does not freeze them.
- **Con — the body-borne idempotency key is not visible to anything between the client and the handler.** Proxies, gateways, and generic HTTP retry middleware that understand the conventional `Idempotency-Key` header see nothing here, and every oRPC call is a `POST` to one path, so no infrastructure layer can deduplicate or route on it. Adding a header alias later is additive, but the body field can never be removed without a breaking change to the published input schema.
