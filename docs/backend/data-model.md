# Data model overview

The core entities and how they relate, at a product level — not the full schema (see `packages/db` and `db-architecture-guard` for schema-level detail). This is the map a new engineer reads before touching any table.

## Core entities

| Entity | Owns | Key relationships |
|---|---|---|
| `organization` (+ `member`, `invitation`) | The tenancy boundary. Better Auth's organization plugin owns these tables (`packages/db/src/schema/organization.ts`); `packages/auth` registers the plugin. | Every ledger table below carries `org_id` with a real FK to `organization.id`. `member` links a `user` to an `organization` with a role string (`owner`/`admin`/`member` — Better Auth's own defaults; not yet reconciled with `ledger.md`'s `admin`/`viewer`, see Phase 4 note below). |
| `ledger_account` | A named balance within one org, in one ISO-4217 currency, with a `type` (`normal` — may never go negative — or `external` — a funding/liability account that may). Holds the **materialized balance**. | Belongs to one `organization`. Has many `ledger_posting` rows (its history). Unique per `(org_id, name)`. |
| `ledger_transaction` | One atomic, balanced economic event — the record that ties a set of postings together. | Belongs to one `organization`. Has many `ledger_posting` (≥2). Self-referential `reverses_transaction_id` links a reversal to the transaction it undoes. `created_by` references the acting `user`. |
| `ledger_posting` | One leg (debit or credit) of a transaction against one account — a positive amount plus a direction. Append-only: the actual source of truth a balance is computed from. | Belongs to one `ledger_transaction` and one `ledger_account`, both enforced by composite `(id, org_id)` foreign keys so a posting's `org_id` can never disagree with the org that actually owns its transaction or account. |
| `ledger_idempotency_key` | A client-supplied retry token: one `(org_id, key)` may ever be reserved. | Belongs to one `organization`. Points at the `ledger_transaction` it ended up producing once that transaction exists (`NULL` until then, and forever `NULL` for a rejected attempt). |
| `ledger_audit_entry` | One record of an attempt to post — successful or rejected. `outcome` (`posted`/`rejected`) discriminates; "the rejections list" is a filtered read against this same table, not a separate one. | Belongs to one `organization`. `actor_user_id` references the acting `user`. `transaction_id` is set for a posted attempt, `NULL` for a rejected one; `reason` and `metadata` (jsonb) capture why a rejection happened. |

## Lifecycle notes

- **Org is the isolation boundary.** Every ledger table above carries `org_id` and every read/write is expected to filter by it. `ledger_posting`'s account/transaction references go further than a plain FK: they are composite `(account_id, org_id)` / `(transaction_id, org_id)` foreign keys, so the database itself — not just repository code remembering a `WHERE org_id = ...` — rejects a posting whose org disagrees with the org that owns its account or transaction.
- **Postings are append-only.** A `ledger_posting` row is never updated or deleted once written; database triggers enforce this directly (`UPDATE`, `DELETE`, and `TRUNCATE` are all rejected). The only sanctioned correction is a **reversal**: a new `ledger_transaction` with mirrored debits/credits, linked back via `reverses_transaction_id`. History is never edited, only added to.
- **Balance is materialized, and reconciliation is a continuously-checkable invariant, not a periodic job.** `ledger_account.balance` is kept in sync with its postings inside the same database transaction that writes them. `signed Σ(postings) == balance` can be (and is, in tests) recomputed and checked at any time — there is no scheduled reconciliation sweep this depends on; the guarantee is meant to hold at every moment, not just after a batch job runs.
- **A transaction posts atomically or not at all.** Locking the involved accounts, checking funds, inserting postings, and updating balances all happen inside one database transaction. A failure at any point rolls back every part of it, including the idempotency key reservation — so a failed attempt never leaves a partial transaction, a stray posting, or a stuck idempotency key behind.
- **A rejected attempt is still recorded, but via a second, separate transaction.** Since the failing attempt's own transaction rolls back everything written inside it, an audit row placed there would vanish along with the failure. So the rejection audit entry (`outcome = 'rejected'`) is written in its own transaction after the failing one rolls back — the one place "the write is atomic" and "the failure is still recorded" require two transactions instead of one. See ADR 0003 for the full reasoning.
- **The idempotency key is reserved before the transaction it backs exists**, and is backfilled with the resulting `transaction_id` once that transaction is created. A rejected attempt never backfills it, and the reservation itself rolls back with the rest of the failed attempt — so a caller can safely retry the same key after a rejection. See ADR 0004 for why the reservation is a blocking `INSERT`, not `ON CONFLICT DO NOTHING`.
- **Financial provenance outlives the acting user.** `ledger_transaction.created_by` and `ledger_audit_entry.actor_user_id` reference `user.id` with no delete cascade, so a user who has ever posted or been audited cannot currently be hard-deleted without a foreign-key violation. This is deliberate (see ADR 0003's Consequences) but has no resolved "deactivate vs. delete" story yet — a Phase 4+ concern.
- **Role interpretation is deferred.** `member.role` is stored (Better Auth's `owner`/`admin`/`member` defaults) but nothing in this phase enforces or maps it to `ledger.md`'s `admin`/`viewer` model — that mapping, and any permission check based on it, is Phase 4's responsibility.
