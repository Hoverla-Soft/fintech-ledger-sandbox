## Approved decisions

**D1 — Playwright lives in `apps/web`, not a new workspace.** The console is the thing being driven. A dedicated `e2e` workspace would need its own manifest, tsconfig, and lint wiring to test an app it does not own.

**D2 — the specs drive the real signup flow rather than injecting a session.** Seeding a user directly and forging a Better Auth cookie would be faster and considerably more brittle: it would couple the suite to Better Auth's session encoding and would skip the `/login → /organization → console` routing that `_auth/route.tsx` implements and that ADR 0009 reasons about. That routing *is* one of the behaviours worth testing. Each spec file creates its own uniquely-named user, so specs never contend over shared state.

**D3 — no `reset()` between specs; isolation comes from unique tenants.** The sandbox `reset` procedure is org-scoped and the API suite already covers it. Truncating shared tables from a browser test would make specs order-dependent and unable to run in parallel. A fresh org per spec file gives isolation for free, and matches how the API's own integration suites work.

**D4 — no CI e2e job at all, revised from the draft.** The draft said the job would be added with `continue-on-error: true`. On reflection that was the wrong call for a different reason than flakiness: the suite has only ever run locally, so committing a CI job for it would be shipping a check that has **never been executed in the environment it claims to check** — the precise thing Phase 6a existed to eliminate. A non-blocking job that has never run is not a weak check, it is an unverified one. Recorded as open question #9's remaining work instead.

**D5 — a flaky spec is deleted, not retried.** Specs driving account creation and transfer/reversal were written and run. They passed on one run and failed the next against unchanged code: the account and type pickers are Base UI `Select` components whose listbox stays mounted after selection, so locators resolve to two elements or to a stale overlay depending on timing. The available responses were to add retries, to add waits until it looked stable, or to remove them. Retries would have hidden real flakiness inside a ledger's own test suite; "wait until it passes" is how a suite becomes something people re-run rather than read. They are removed, and the uncovered flows are named explicitly in `docs/test-coverage.md` and open question #9.

## Verification

```bash
pnpm lint
pnpm check-types
pnpm test
pnpm build
node .claude/scripts/migration-integrity-guard.js --check
pnpm test:e2e
```

Baseline to beat, measured after 6b: `lint` exit 0 (221 files), `check-types` 6/6, `test` 598 passed (73 core + 259 web + 28 db + 238 api), `build` 2/2, guard PASS.

**Result, verified 2026-07-28:** `lint` **exit 0** (225 files) · `check-types` **6/6 green** · `test` **598 passed** (73 core + 259 web + 28 db + 238 api — unchanged, confirming Vitest does not collect `e2e/`) · `build` **2/2 green** · migration guard **PASS** · `test:e2e` **3/3 passed, twice in a row** against the same database with no reset (16.0s, then 11.1s).

**What shipped:** the Playwright harness — config with a two-server `webServer`, a sign-up/org helper, Chromium — and **3 specs**: the unauthenticated redirect, sign-up → `/organization` → console, and the accounts empty state.

**What did not, and why.** Specs for account creation and for transfer + reversal were written and run. They passed, then failed on the next run against unchanged code. The cause is the Base UI `Select` used for account type and for transfer endpoints: its listbox stays mounted after selection, so locators resolve to two elements or to a stale overlay depending on timing. Three options existed — add retries, add waits until it looked stable, or delete. The first hides genuine flakiness inside a ledger's own test suite; the second produces a suite people re-run rather than read. They were deleted, and the gap is named in `docs/test-coverage.md`, in open question #9, and in the Acceptance criteria above where the unmet items are struck through rather than reworded to match what shipped.

This is the outcome the design flagged as most likely to slip, and it slipped in exactly the predicted place. The harness is the durable part: adding a spec is now a file, not a project.

**Also not done:** no CI e2e job (D4 as revised — a job that has never run in CI is an unverified check, which is what 6a existed to remove), no viewer-role coverage, no reconciliation/sandbox/audit specs. The Phase 5 manual demo scripts are **not** retired.
