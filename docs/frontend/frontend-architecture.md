# Frontend architecture

The console (`apps/web`) — how it is laid out, where each kind of logic belongs, and which rules are load-bearing rather than stylistic. Filled in Phase 5a; the sections describing rendered behaviour are extended by the slices that produce it.

## App structure

The target layout for the finished console. As of Phase 5a only `lib/ledger/`, `test/`, `routes/`, `components/` (flat), and `utils/` exist — `features/`, `components/shell/`, `components/states/`, and `lib/org/` are created by the slices that first need them (5b onward). It is written out in full here so those slices place files consistently rather than each inventing a layout.

```text
apps/web/src/
  routes/              # TanStack Router file-based routes. Thin: a route wires
                       # params, loaders, and guards to a feature component and
                       # does nothing else.
  features/<domain>/   # Screen-scoped components and hooks. Owned by one screen;
                       # not shared. `accounts/`, `transfer/`, `transactions/`,
                       # `reconciliation/`, `sandbox/`, `audit/`.
  components/shell/    # App-wide chrome: header, nav, org switcher, user menu.
  components/states/   # The loading / empty / error trio every screen composes.
  lib/                 # Cross-cutting logic. No JSX in this directory.
    ledger/            # Money, transaction composition, idempotency, error copy.
    org/               # Active organization and role resolution.
  test/                # Suite setup. Not shipped.
  utils/orpc.ts        # The typed client and TanStack Query utils. One instance.
```

`routeTree.gen.ts` is generated by the TanStack Router Vite plugin and is never hand-edited. It regenerates during `pnpm check-types` (which runs `vite build`), so any task adding a route must include it in Scope.

### Where logic goes, and why it is not negotiable

`docs/development/coding-rules.md` — *"Keep API/business logic out of UI components — components render and dispatch, they don't decide."* In a ledger console that rule has teeth:

- **Money arithmetic and formatting** live in `lib/ledger/amount.ts`. Never `Number`, never `parseFloat`, never `toLocaleString` on an amount — see `docs/adr/0002-money-representation.md`.
- **Transaction composition** lives in `lib/ledger/postings.ts` and nowhere else. ADR 0006 made the console responsible for building a *balanced* postings array, and a balanced-but-inverted array is accepted by the server, moves real money, and produces no error. Composition is therefore pinned by a fixture derived from `packages/api/src/sandbox/scenarios.ts`, not re-derived at each call site.
- **Idempotency keys** live in `lib/ledger/idempotency.ts`. Minted when an operation starts, never during render, reused byte-for-byte on retry. A re-minted key posts twice (`docs/adr/0006-write-endpoint-contract.md:17`).
- **Error interpretation** lives in `lib/ledger/errors.ts`. Components switch on the returned `disposition`, never on a raw server `message` — `docs/backend/error-handling.md` makes `data.reason` the contract and `message` explicitly not one.

## State management

Libraries are declared in `docs/development/tech-stack.md` → Companion libraries. The boundary:

- **Server state lives in the TanStack Query cache and is never copied into React state.** Balances, accounts, and transactions are authoritative on the server and change underneath the console — a reset alone rewrites every balance in the org. A component holding a copied balance renders a number the ledger no longer agrees with, which is the one thing this product cannot do.
- **Client state is local by default** — form values, dialog open/closed, the cursor stack for pagination. `useState` in the owning component; lifted only when a sibling genuinely needs it. There is no global store, and none should be added without a documented need.
- **The active organization is session state owned by Better Auth**, not application state. It is changed through `authClient.organization.setActive` and read back from the session — never mirrored into a store, because the server derives `orgId` from a verified `member` row and a client copy could disagree with it (`docs/adr/0005-tenant-isolation.md`).
- **Switching organization or signing out must clear the query cache.** The cache is keyed by procedure and input, not by tenant, so org A's accounts would otherwise still be resident when org B renders.
- **Role is an affordance hint, never an authorization decision.** `docs/product/roles-and-permissions/ledger.md` — *"'The frontend hides the button' is not enforcement anywhere in this system."* Every write path handles `403 insufficient_role` regardless of what the UI chose to render, because a role can be revoked mid-session and is re-read per request.

## Data fetching

- Reads go through `@orpc/tanstack-query` utils built on the single client in `utils/orpc.ts`. No second client, no bare `fetch` to `/rpc`.
- Every fetch renders a skeleton, and empty is visually distinct from failed-to-load, with a working retry on the latter (`docs/product/requirements/ledger.md:73-75`). The primitives for this live in `components/states/`.
- Mutations invalidate the queries they affect rather than writing into the cache by hand — a posted transaction changes balances on accounts the mutation response does not fully describe.
- Cursor pagination echoes the server's opaque cursor verbatim. It is base64url and is never constructed, parsed, or incremented client-side; `400 invalid_cursor` resets to the first page with a notice rather than rendering a silent empty result.

## Shared components and design system

`packages/ui` is the shared design-system boundary. Its actual shape:

```text
packages/ui/src/
  components/   # primitives and composed design-system components
  hooks/        # shared hooks
  lib/          # utilities (cn, variant helpers)
  styles/       # globals.css — reset, Tailwind v4 @theme, design tokens
```

This diverges from the template's suggested `tokens/`, `themes/`, and `icons/` directories: tokens and theme definitions are CSS custom properties inside `styles/globals.css` (Tailwind v4's `@theme` model rather than a JS token module), and icons come from `lucide-react` directly rather than through a re-export surface. Recorded here rather than restructured, since no consumer benefits from the move.

**Import form.** `packages/ui` exposes **per-file subpath exports only** — there is no `.` root export:

```ts
import { Button } from "@fintech-ledger-sandbox/ui/components/button";
```

Importing `@fintech-ledger-sandbox/ui` bare will not resolve. Apps must not reach past the declared subpaths into `src/`, and `apps/web/tsconfig.json` deliberately carries **no** `paths` alias for the package — an alias would shadow the real export map and hide a broken one (`docs/development/architecture.md`).

**What belongs there.** Reusable primitives and the common visual language. Routes, screens, layouts, and feature-specific compositions stay in the owning app. Primitives are added by the slice that first renders one, not speculatively ahead of a consumer.

**Provenance.** Components are generated by the shadcn CLI (`packages/ui/components.json`, style `base-lyra`) and are built on **Base UI** (`@base-ui/react`), which composes via a `render` prop — not Radix's `asChild`.
