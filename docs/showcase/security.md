# Security checklist

This is a sandbox — the money is fake, the discipline is not. Every control below is either enforced in code you can open, proven by a test you can run, or honestly marked ⚠️ as not done yet. Nothing here is aspirational: "Enforced in" links to the real enforcement point, and "Proven by" links to a real test or ADR — or says `manual` when no automated proof exists.

## Threat model & scope

This sandbox defends the properties a ledger must never lose — balance integrity, tenant isolation, idempotency, an unerasable audit trail — against any caller of its API, including a hostile authenticated one. It deliberately does **not** defend against:

- **A compromised host or database credential.** Anyone with direct SQL access bypasses the API middleware entirely; only the composite foreign keys and immutability triggers survive that (see [ADR 0005](../adr/0005-tenant-isolation.md)'s consequences — this is a recorded boundary, not an oversight).
- **Network-layer denial of service.** Rate limiting is keyed by verified org/user identity, which by design means unauthenticated traffic is never rate-limited here — that is a job for infrastructure in front of the process, which a single-process sandbox does not have.
- **Real-money threats.** There is no PCI scope, no encryption-at-rest requirement, no payment data. `SameSite=None` cookies and a permissive local cookie posture are tuned for a cross-origin demo console, and would need revisiting alongside the ⚠️ rows above before anything resembling production.
