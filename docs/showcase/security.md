# Security checklist

This is a sandbox — the money is fake, the discipline is not. Every control below is either enforced in code you can open, proven by a test you can run, or honestly marked ⚠️ as not done yet. Nothing here is aspirational: "Enforced in" links to the real enforcement point, and "Proven by" links to a real test or ADR — or says `manual` when no automated proof exists.

| **Ledger immutability** — posted rows cannot be mutated even by privileged SQL: database triggers reject `UPDATE`, `DELETE`, and `TRUNCATE` on `ledger_posting`; correction is only via linked reversing transactions | ✅ | [`packages/db/drizzle/0002_ledger_posting_immutability_trigger.sql`](../../packages/db/drizzle/0002_ledger_posting_immutability_trigger.sql) | [`ledger-immutability.test.ts`](../../packages/db/src/schema/ledger-immutability.test.ts) — issues the forbidden statements against real Postgres and asserts rejection |
| **Security response headers** — `nosniff`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: no-referrer`, `Cross-Origin-Resource-Policy: same-origin`, `X-Powered-By` removed; HSTS asserted **only** in production, since this server is plain http locally and a header claiming "HTTPS only" from an http origin is a lie waiting to be copied into a real config. **CSP is `default-src 'none'`** on everything this origin returns — which is JSON, and needs no subresources at all — plus `frame-ancestors`, `base-uri`, and `form-action` at `'none'` (none of which inherit from `default-src`). | **Graceful shutdown** — `SIGTERM`/`SIGINT` stop accepting connections, drain in-flight requests, close idle keep-alive sockets, then end the pool, in that order: closing the pool first would fail the very requests the drain exists to protect, including one mid-transaction. Idempotent, with a 10s force-exit so a stuck drain cannot outlive the platform's grace window. `uncaughtException`/`unhandledRejection` route through the same path and **exit** — after an unhandled rejection the process holds state nobody reasoned about, and Postgres is the authority on every balance, so dying loses nothing an aborted transaction had not already rolled back | ✅ | [`apps/server/src/index.ts`](../../apps/server/src/index.ts), pool ownership in [`packages/api/src/context.ts`](../../packages/api/src/context.ts) (`closeDatabasePool`) | manual (signal handling is process-level; the suite covers the app, not the listener) |

## Threat model & scope

This sandbox defends the properties a ledger must never lose — balance integrity, tenant isolation, idempotency, an unerasable audit trail — against any caller of its API, including a hostile authenticated one. It deliberately does **not** defend against:

- **A compromised host or database credential.** Anyone with direct SQL access bypasses the API middleware entirely; only the composite foreign keys and immutability triggers survive that (see [ADR 0005](../adr/0005-tenant-isolation.md)'s consequences — this is a recorded boundary, not an oversight).
- **Network-layer denial of service.** Rate limiting is keyed by verified org/user identity, which by design means unauthenticated traffic is never rate-limited here — that is a job for infrastructure in front of the process, which a single-process sandbox does not have.
- **Real-money threats.** There is no PCI scope, no encryption-at-rest requirement, no payment data. `SameSite=None` cookies and a permissive local cookie posture are tuned for a cross-origin demo console, and would need revisiting alongside the ⚠️ rows above before anything resembling production.
