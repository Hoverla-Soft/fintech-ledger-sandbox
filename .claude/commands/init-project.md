This repo is `claude-setup-template` copied into a new project. Walk the user through filling in every `{{PLACEHOLDER}}` across `CLAUDE.md`, `docs/development/architecture.md`, `docs/development/tech-stack.md`, `docs/development/infrastructure.md`, `docs/development/skills-and-plugins.md`, `docs/development/work-systems.md`, `docs/development/testing-rules.md`, `docs/development/coding-rules.md`, and applicable `docs/operations/` files.

Ask for, in order, then edit the files:

1. Project name and one-line description → `CLAUDE.md`
2. Package manager and the exact install/lint/typecheck/test/dev commands (check `package.json` scripts if this is an existing repo rather than asking blind) → `CLAUDE.md`
3. The real package list and what each owns → `docs/development/architecture.md`'s boundary table, replacing the default assumed shape
   a. Inventory every frontend app and determine whether they share a compatible framework/runtime and visual system.
   b. For two or more compatible frontend apps, declare one `packages/ui` (or one explicitly named equivalent) that owns reusable components, tokens, themes, shared/global styles, and icons. Keep these as modules inside that package rather than creating a package per concern.
   c. Record app-local ownership for routes, screens, layouts, feature components, and app-only styles. If the frontends are incompatible, document the reason and their separate UI boundaries instead of forcing a shared package.
4. **Tech stack** → `docs/development/tech-stack.md`:
   a. Fill the **Core** table first: package manager, monorepo tool, language, frontend framework, backend framework, database, ORM, and runtime/deployment target. Use `none` explicitly rather than leaving a row blank when something doesn't apply.
   b. For each core choice made, open `docs/development/framework-companions.md` and ask the relevant companion questions as real choices: routing, state, forms, validation, API layer, auth/session framework, identity protocols/providers, CSS/styling, UI primitives, component library, logging, error monitoring, metrics/tracing, and testing. Don't default to "whatever's most popular."
   c. Fill the **Companion libraries** table in `tech-stack.md` from the answers.
   d. Reconcile relevant installed dependencies with stack choices by checking workspace manifests, the lockfile, nearby imports, and shared utilities. Prefer and document an established pattern; flag packages that appear unused, legacy, duplicated, or inconsistent. Installation alone is not proof that a package is the chosen standard.
   e. Once a row has a real answer, check whether its package is installed in the relevant workspace. If not, explain why it applies and ask whether to install it; only run the install after approval.
   f. Check off `tech-stack.md`'s Status checklist once nothing's left as `{{...}}` (or explicitly `none`) and installs are done.
   g. Discover optional framework best-practice skills/plugins only after stack versions are confirmed. Follow `docs/development/skills-and-plugins.md`: inventory extensions; audit all skills, agents, hooks, commands, MCP/LSP components, scripts, settings, permissions, and dependencies; map framework major version, runtime/router assumptions, companions, paths, conflicts, and overrides; present benefit, source, scope, and risks; install only after approval. Choose implementation reference, review guard, explicit workflow, or isolated experiment deliberately. Update agents and guard routes only when required, preserving existing guards and first-match routing. Run `/reload-plugins` or restart, smoke-test gating and permissions, and record source/version/integration/status.
   h. Discover the team's work systems and MCP/connectors for tasks, product docs, design, source control/reviews, and communication. Follow `docs/development/work-systems.md`'s Claude Code bootstrap: inventory with `claude mcp list/get`; choose local/user/project scope; propose `claude mcp add` only for a server the user approves; use `/mcp` for project approval, OAuth, status, and exact tool names; restart/reload if the current session cannot see the new server. Fill the document with the exact source of truth, transport/scope, stable workspace/project, access mode, and fallback. Merge existing `.mcp.json`/MCP configuration without overwriting servers, permissions, hooks, or credentials.
   i. Add only the exact discovered read-tool names (`mcp__<server>__<tool>`) to the `allowed-tools` frontmatter of the commands/agents that need them, following the ownership map in `work-systems.md`. Prefer exact read tools over server wildcards; keep mutation tools prompt-gated unless the user explicitly approves a narrow write workflow. Keep `ToolSearch` available for deferred MCP discovery.
   j. After configuration is loaded, call one representative read tool for each connector. Verify the returned workspace/project and stable artifact ID, record the result and date, and leave the connector unverified if authentication, permissions, tool discovery, or the read call fails. Do not test writes without explicit permission.
   k. Discover infrastructure from actual CI workflows, Docker/container files, IaC modules/state configuration, platform/deployment config, environment schemas, and operations docs. Fill `docs/development/infrastructure.md`, `docs/operations/deployment.md`, and `docs/operations/runbook.md` with the real provider/topology, environments, ownership, CI/CD, artifact promotion, approvals, secrets, networking, runtime resources, observability, rollout/rollback, backups/restore, RPO/RTO, incident escalation, and cost/capacity controls. Mark non-applicable surfaces `N/A: <reason>` rather than inventing Kubernetes, containers, or IaC. Record safe format/lint/validate/plan/render commands; do not apply/deploy/destroy, access production data, rotate secrets, or run recovery procedures during initialization.
5. Scaffold the real packages/apps using the boundary table from step 3 and the confirmed monorepo tool/package manager from step 4:
   a. For every declared package/app path that does not exist, create a minimal `package.json` whose name matches the path and has `private: true`; implement that package's `lint`, `typecheck`, `test`, and `build` scripts declared in `CLAUDE.md`, plus `dev` for runnable apps and consumed workspace packages. Package scripts must run the package's actual tools and must not copy root orchestration commands verbatim.
   b. Add a `tsconfig.json` extending the shared base config when one exists, and an empty entry file that matches the declared framework/runtime. For consumed workspace packages, configure the declared compiler/bundler to emit runtime files and declarations to `dist`; map `package.json` runtime/type exports and every public subpath to that output. Do not expose `src` or add consumer aliases to package source. Do not invent framework-specific scaffolding for an undeclared framework.
   c. For existing paths, never overwrite them. Confirm that each has a `package.json`, is registered in the declared package-manager/monorepo workspace config, and exposes the expected script names; fill only missing pieces while preserving existing scripts and configuration.
   d. Register every new package/app in the actual workspace config, use the package manager's workspace dependency convention for consumers, run the declared install command so the lockfile records it, and then run the smallest relevant package-level checks.
   e. Report separately what was created, what was completed in existing packages, what was left untouched, and any scaffold/check that remains blocked.
   f. When the boundary table declares the shared UI package, scaffold or complete its public entry points and internal directories for components, tokens, styles, themes, and icons. Use the confirmed styling/component choices, do not invent framework-specific implementation, and do not overwrite existing design-system code. Ensure each compatible frontend app depends on the workspace package and consumes only its public exports.
   g. Give each consumed workspace package a `dev` script that runs its owning compiler/bundler in watch mode and performs an initial build into `dist`. Configure the root `dev` orchestration to run those watchers together with dependent apps. Verify one package from a clean `dist`, resolve its public entry point from a real consumer, then smoke-test that a source change refreshes `dist` without restarting the watcher; revert the smoke-test change and do not commit generated output.
6. Whether this project integrates third-party providers now or later → if yes, note them in `docs/development/architecture.md` and create `docs/integrations/<provider>.md` from `docs/integrations/TEMPLATE.md` per provider (don't fill provider details yet unless the user has them ready — an empty copy is fine as a placeholder)
7. Test framework, test types, locations, and exact test/watch commands → both `docs/development/testing-rules.md` and `docs/test-coverage.md` (don't ask twice; copy the confirmed answers).
8. Fill the project-specific frontend/backend docs that apply: `docs/frontend/frontend-architecture.md`, `docs/frontend/forms-and-validation.md`, `docs/frontend/ui-states.md`, `docs/backend/api-flow.md`, `docs/backend/data-model.md`, and `docs/backend/error-handling.md`. Mark an entire surface `N/A: <reason>` when the project has no frontend/backend rather than leaving ambiguous placeholders.
9. Update `.claude/guard-routes.json` to match the real package/app paths from step 3. Preserve specific-before-general ordering, keep the generic configuration and infrastructure routes that apply to the selected tools, remove only demonstrably inapplicable tool-specific routes, and ensure every implementation area routes to the relevant guards.
10. Inventory the project's configuration files. Inspect every root and workspace `tsconfig*.json` (including `extends` chains and project references), `package.json`, workspace/monorepo config, and applicable lint, test, build, bundler, framework, deployment, and environment-schema config. Confirm that paths, aliases, include/exclude rules, module/target settings, package boundaries, and referenced files/packages match the real repository. Confirm consumed packages resolve runtime and types through public exports under `dist`, root dev orchestration runs their watch builds, and no alias bypasses the package boundary by pointing consumers at another package's `src`. Preserve deliberate differences between app/package configs; report unexplained conflicts or stale paths.
11. Validate configuration with the owning tool wherever possible: parse JSON/JSONC with an appropriate parser, run TypeScript with the project's actual `tsc`/typecheck command so extended configs and references are resolved, and use each tool's supported config inspection or dry-run command when available. Do not claim a config is valid merely because it parses as JSON. Never print secret values while inspecting environment configuration.
12. Confirm `CLAUDE.md` has exact install, lint, typecheck, test, build, and dev commands. Run the non-destructive verification commands that are available and report failures rather than marking setup complete.

Use `Grep` to confirm no `{{...}}` placeholders remain in initialized project docs (excluding example/template files intended to retain placeholders). Report anything you couldn't fill as a short list; the project is not loop-ready while required commands, package boundaries, guard routes, applicable tech/docs, infrastructure/environment/operations decisions, required skill/plugin integrations, work-system authority/connectors, or configuration validation remain unresolved.

If $ARGUMENTS was given, use it as the project name and skip asking for that one.
